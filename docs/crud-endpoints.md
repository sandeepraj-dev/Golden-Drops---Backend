# CRUD endpoints (fixed)

Base URL: `/api/v1`. Except `/auth/setup-admin`, `/auth/login`, and `/health`, requests require `Authorization: Bearer <token>`. Master-data create/update/deactivate operations require ADMIN or MANAGER. Deletion is a **soft delete** (`isActive=false`) so historical accounting records remain intact.

## Master data CRUD

| Resource | Collection endpoint | Fields commonly used |
|---|---|---|
| Customers | `/customers` | `name`, `phone`, `alternatePhone`, `address`, `villageOrCity`, `notes`, `openingBalance` (opening balance adjustment is restricted on update) |
| Suppliers | `/suppliers` | `name`, `phone`, `address`, `notes`, `openingBalance` |
| Oil types | `/oil-types` | `oilName`, `description`, `unit` (`KG`), `lowStockThresholdKg` |
| Oil storage locations | `/storage-locations` | `locationName`, `description` |

For each resource:

- `GET /{resource}?page=1&limit=20&q=search&isActive=true` — list/search/paginate.
- `POST /{resource}` — create.
- `GET /{resource}/:id` — fetch one.
- `PATCH /{resource}/:id` — partial update.
- `PUT /{resource}/:id` — compatibility alias for the same partial-update behavior.
- `DELETE /{resource}/:id` — soft-deactivate; it does not physically remove records.

Business codes (`customerCode`, `supplierCode`, `oilCode`, `locationCode`) are generated by model hooks when omitted. Do not send `openingBalance` in an update; use the controlled opening-balance workflow.

## Example requests

Create an oil type:
```http
POST /api/v1/oil-types
Authorization: Bearer <token>
Content-Type: application/json
```
```json
{"oilName":"Groundnut Oil","description":"Filtered groundnut oil","unit":"KG","lowStockThresholdKg":50}
```

Update a storage location:
```http
PATCH /api/v1/storage-locations/65f000000000000000000001
Authorization: Bearer <token>
Content-Type: application/json
```
```json
{"locationName":"Main Warehouse","description":"Rear storage area"}
```

Deactivate a customer:
```http
DELETE /api/v1/customers/65f000000000000000000001
Authorization: Bearer <token>
```

Successful responses use `{ "success": true, "data": ... }`; list responses also include pagination metadata. A missing record returns 404, invalid IDs return a validation error, and model validation errors are handled by central error middleware.

## Other existing resource operations

- Users: `GET/POST /users`, `PATCH /users/:id` (ADMIN only).
- Oil prices: `GET/POST /oil-prices`, `PATCH /oil-prices/:id/close`.
- Purchases, sales, payments, expenses, stock and daily stock have transaction-specific routes documented in `/api-docs` when OpenAPI is configured. Financial transactions should not be edited or deleted as generic CRUD: use reversal/audit workflows where provided, to preserve stock and accounting ledgers.

## What was fixed

The previous router registered two catch-all `PATCH /:id` and `DELETE /:id` handlers for customer and oil type after all other routes. Those routes did not identify a resource and could incorrectly capture unrelated requests. They were removed; the consistent parameterized master-resource routes are now the single source of truth for customers, suppliers, oil types, and storage locations. `PUT` aliases were added for update compatibility.
